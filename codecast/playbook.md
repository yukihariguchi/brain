## 全社戦略

### 何をやるか

可愛い子 × メディア戦略で集客し、可愛い子がモノ・ヒトを売れる仲介領域に集中する。

- 領域: 誰が仲介してもバリューが変わらない領域（現在は人材）。仲介者の技量で結果が変わらない以上、勝敗は集客力で決まる
- 集客: Netflix の Selling Sunset のような YouTube 自社メディア
- 前提: 可愛い子には夜職以外で稼げる職業がない。昼で稼げる仕組みを作れば、大量に採用できる
- 事業: 人材紹介 ― CodeCast

### エンジン

勝ち筋は「メディアで集めた在庫を、その場の取引で消費せず、閉じた自社PFに蓄積して資産化する」こと。
発見・マッチングは AI でコモディティ化する。コピーできないのは在庫の流動性だけ。だから設計はすべて「在庫をどこに溜めるか」に従属する。

### ブランドポジショニング

「真面目なビジネス × たまたま可愛い子が多い」。
港区感・夜職感を出さず、顧客・取引先双方の信頼を担保する。可愛い子は集客のアクセントであって、前面に出すフックにはしない。事業の中身は業界の専門性で勝負する。
判断に迷ったら「専門性が前面に出ているか」で決める。

- YouTube の CA 出演は月1〜2本のスポット。メイン司会・聞き手は専門性のある人物
- CA の X はノウハウ系を主軸（ノウハウ6／日常3／案件1）
- スポンサー出展は専門メンバーを必ず同席させ、女性だけのブースにしない
- 避ける: 私生活全開・夜の街・ブランド品系の投稿／可愛さを前面に出した販促物／容姿に依存した動画タイトル・サムネイル

## CodeCast

### プロダクト構成

| 名称 | 誰が使うか | 中身 |
|---|---|---|
| CodeCast | 候補者 | 候補者の正本。プロフィール・職務経歴書・いいね/スカウト・副業の稼働管理 |
| CodeCast Hire | 企業 | CodeCast の登録者を検索し、いいねを送り、マッチングした候補者にスカウトを送る |
| Admin | 社内 | 候補者管理、配信、経路分析、トスアップ運用 |
| 公式LINE | 候補者 | リーチ層。プロフィールの正本は持たず、CodeCast へ送る |

「CodeCast」1ブランドで IT 業界の全職種を扱う。「Code」を IT 業界の代名詞に意味拡張し、Product 系も Biz 系も1つの世界観に統合する。候補者・企業から見た接点は1ブランドに統一し、CA だけが職種別に分業する。

候補者向けはブランド名そのまま「CodeCast」、企業向けだけを「CodeCast Hire」と呼び分ける。候補者にサービス名を覚え直させないための非対称な命名で、候補者から見れば「CodeCast に登録する」で完結する。企業向けだけが修飾語を持つのは、候補者側が本体だという構造をそのまま表している。以降、単に「CodeCast」と書くときは候補者側を指す。

#### ドメイン ― LP とアプリを分ける

| | LP（未登録者の入口） | ウェブアプリ（ログイン後の正本） |
|---|---|---|
| CodeCast（候補者） | codecast.jp | app.codecast.jp |
| CodeCast Hire（企業） | hire.codecast.jp | hire-app.codecast.jp |

※ 候補者向け LP の正式ドメインは codecast.jp。媒体リリースまでは lp.codecast.jp に置く（2026-10-04）。会社 HP は company.codecast.jp（base.md 参照）。

入口と正本を別ドメインに置く。LP は未登録者を口説く場所、アプリはログインした人が毎週戻ってくる場所で、更新の頻度も速度も求められるものが違う。分けておけば、LP の文言差し替え（職種の開放ごとに発生する）とアプリのデプロイが互いを止めない。認証スコープと計測も混ざらない。

候補者と企業のアプリも分ける。同じ画面に両者を同居させると、権限設計が常に条件分岐になり、片方の変更が片方の事故になる。ドメインで割っておけば、企業に見せる面（Hire）と候補者の正本（CodeCast）を独立して作れる。

CTA の行き先は1つに揃える。codecast.jp の「無料で会員登録」も、公式LINE のリッチメニューも、イベント申込も、行き着く先は app.codecast.jp の登録フォーム。入口が何本あっても正本は1つで、経路の違いは流入元パラメータとしてだけ残す。

※ スキルシート作成ツールは skillsheet.codecast.jp。利用に会員登録が必要なため実質 app.codecast.jp の一機能で、統合するか別ドメインのまま残すかは未決。

#### 職種は、在庫が溜まった順に開放する

全職種を同時には開けない。Hire の商品は DB の厚みなので、候補者が薄い職種を検索対象に出すと、いいねがマッチングにならず「その職種はいない媒体」という評価が最初につく。一度ついた評価は、後から在庫が厚くなっても簡単には戻らない。

そこで受け入れと開放を分ける。

| | 対象 | ルール |
|---|---|---|
| CodeCast（受け入れ） | IT 業界の全職種 | 最初から制限しない。登録・プロフィール・職務経歴書・稼働管理はすべての職種で使える |
| CodeCast Hire（開放） | 在庫規律を満たした職種のみ | エンジニアから始め、溜まった職種を順に検索軸へ追加する |

未開放の職種も、CodeCast には溜め続ける。企業からのいいね・スカウトは届かないが、職務経歴書の作成と副業の稼働管理は使える。この2つは単体で再訪の理由になるため、開放前でもアクティブなまま在庫が積み上がる。開放した瞬間、その職種は「今日集め始めた母集団」ではなく「すでに溜まっている母集団」として企業に出せる。

開放の判断は在庫規律と同じ指標で行う。職種別の「アクティブ候補者数 ÷ 契約社数」が下限を満たせるところまで積み上がったら、その職種を Hire の検索軸に追加する。同じ指標が「開けるか」と「これ以上売れるか」の両方を決める。

Hire LP（hire.codecast.jp）は、開放済みの職種だけを名乗る。現在はエンジニア採用の LP として書く。未開放の職種も、開放予定も書かない。企業に「今いる人」以外を期待させないため。職種が開放されるたびに、LP の見出し・登録者の内訳・人材カードを差し替えていく。CodeCast という1ブランドの器は最初から全職種を前提に作り、表に出す範囲だけを在庫に合わせて広げる。

### 勝ち筋 ― 3つの強み

#### ① メディア（入口の堀・最重要）

非SEO・トラストベースの集客。検索流入に依存せず、ブランドと信頼で候補者を集める。他社が一番苦しむ「候補者の流動性」をここで作る。唯一、本当に固有でコピーされにくい堀。

YouTube・CA の X・食事会という非公開経路から集まるため、他媒体・他エージェントに登録していない層が中心になる。企業が Hire を契約する一次的な理由はここにある。

#### ② 業務効率＝開発 × セールス（転換力）

集めたリードを取りこぼさず売上化する処理能力。開発は CodeCast で CA の生産性を上げ、セールスは CA のクロージングと RA の企業開拓で決める。

CA の 1on1 が在庫の質を作る。候補者のほとんどは CA と 1on1 しており、経歴・スキルは CA が聞き取って入力している。自己申告のみの媒体より情報の密度と正確さが高い。

#### ③ 閉じた CodeCast への在庫蓄積（複利）

②で動かすほど候補者プールが資産として溜まる。この在庫がそのまま Hire の商品であり、契約社数の上限を規定する。

### CodeCast ― 候補者を資産化する

メディアで集めた候補者を、その場の成約で消費せず、閉じた自社PFに蓄積する。勝負どころはプラットフォームの技術ではなく、希少な入力（候補者の流動性）を握ること。閉じていること自体が堀になる。

#### CodeCast に溜め、LINE で起こす

| | 役割 |
|---|---|
| CodeCast（app.codecast.jp） | 正本。プロフィール、いいね/スカウトの履歴、稼働報告、契約、温度データ |
| メール | 基本通知。コストがかからない |
| 公式LINE | リーチ層／温度ゲート。プロフィールの正本は持たず、リッチメニューから CodeCast へ送る |
| 担当 CA の公式LINE | 即レスレール。エージェントがついた候補者と交換する |

LINE に事業を人質に取られず、長期の資産は CodeCast に溜める。温度シグナルは LINE の開封ではなく、CodeCast 上の行動（ログイン・閲覧・いいね反応・稼働報告）から取る。こちらのほうが精度が高い。

#### CodeCast に戻る理由 ＝ 登録させる理由

候補者の「欲しいもの」を、すべて CodeCast のプロフィール入力に変える。データは「マッチングのために教えて」ではなく「あなたに X を渡すために」で取る。次の4つは、登録の give であると同時に再訪のトリガーでもある。

1. いいね・スカウトの受け取り（中核）: 登録すれば企業から声がかかる。面談より摩擦が低く、登録動機として最も強い
2. 職務経歴書の作成: 完成率が高く、入力がそのまま正本になる。最大レバーは「作成」を取材にすること。CA が面談で聞き取って仕上げれば、候補者は楽で、CA は検証済みプロフィールを作れる
3. イベント申込: 申込フォーム＝プロフィール作成
4. 副業の稼働管理（常時アクティブの核）: 毎月の稼働報告でログインが発生する。対象は CodeCast 斡旋分のみ

①が効かない状態が2つある。企業がまだ薄い初期と、Hire に未開放の職種。前者は CA が能動的にいいね相当を供給して埋め、後者は②と④だけで保たせる。未開放の職種にとっては、職務経歴書と稼働管理が登録の give のすべてになる。

### 収益モデル ― CodeCast Hire

1つの閉じた候補者プールの上に、企業向けの単一商品を載せる。候補者から見れば商品は1つで、転職も副業も同じ CodeCast でいいねとスカウトを受ける。

#### 料金

| 項目 | 6ヶ月契約 | 12ヶ月契約 |
|---|---|---|
| 基本利用料 | 48万（月8万換算） | 72万（月6万換算） |
| 正社員転職 | 理論年収の 35% | 同左 |
| フリーランス | 稼働報酬（時給 × 稼働時間）の 15%。初期費用なし | 同左 |
| いいね・スカウト | 無料（いいねは正社員・業務委託それぞれ週30件まで） | 同左 |

#### マッチング ― いいね → スカウト

正社員・フリーランスとも同じ流れ。企業が無作為にスカウトを撃つのではなく、双方が興味を示してから初めてメッセージが始まる。

```
企業が検索 → 企業が「いいね」／候補者が「いいかも」 → マッチング成立
  → 企業がスカウト送付 → 返信 → 面談 → 内定・稼働開始
```

上限は課金ではなく回数で置く。正社員・業務委託それぞれ週30件という枠にする理由は3つ。

- 企業が読めない変動費を作らない。見積もりが基本利用料と成果報酬だけで閉じる
- 無差別ないいねを物理的に抑え、候補者を守る。候補者側の同意（いいかも）が二重のゲートとして効く
- 週次リセットなので、企業には毎週使い切る動機が生まれる。枠そのものが Hire へのログイン習慣を作る

#### 35% で何を売るか

1. ここにしかいない候補者。非公開経路で集めているため、他媒体・他エージェントに出ていない層が中心
2. 人が会って書いた経歴。アルゴリズムによる自動スコアリングではなく、CA が 1on1 で聞き取った情報の密度で勝負する

#### 1契約に含まれるもの

| 系統 | 動くのは誰か | 内容 |
|---|---|---|
| セルフサーブ | 企業 | 検索・いいね・スカウト・求人公開 |
| CA トスアップ | CodeCast | 担当 CA が Slack で候補者を推薦する |

トスアップはセルフサーブの取りこぼしを拾う機能。①Hire を使いこなせていない企業（ログイン頻度が低い、いいねが進んでいない、検索条件が狭い）に CA が直接投げる ②検索に引っかかりにくいが、CA が 1on1 で見て合うと判断した候補者を拾い上げる。

契約上のオプションではなく運用判断とし、料金は変えない。Hire の利用状況を Admin で監視し、低調な企業を優先する。

#### 収益の重心

転職1件（年収600万で210万）＝ 基本利用料35社・月分 ＝ フリーランス10人・月分
※フリーランスは時給1万円 × 月140時間 × 15% ＝ 21万／人・月で換算

- 基本利用料だけでは稼げない。だから基本利用料は「稼ぐ価格」ではなく「社数＝いいねの打ち手を増やす価格」として安く置く
- 転職は単価が大きい分ブレる。着地を安定させるのはフリーランスの稼働人数。売上は3ヶ月移動平均で読む

#### 在庫規律 ― 売っていい社数の上限

DB の厚みが商品そのもの。候補者が薄い状態で企業を増やすと、いいねがマッチングにならず更新率が死ぬ。

職種別に「アクティブ候補者数 ÷ 契約社数」の下限を定め、割り込んだらその職種の新規受注を止める。同じ下限が、未開放の職種を Hire に追加してよいかの判断にもなる。先行指標はいいね→マッチング率で、低下は解約の3〜6ヶ月前に現れる。

#### カニバリは防がない

同じ候補者が正社員転職（35% のショット）と業務委託（15% の MRR）のどちらにも進みうる。候補者の意思で決まり、どちらでも収益になる。転職意欲と副業意欲は別軸で管理する（別人口になりやすい）。

候補者の Hire 上での露出はオプトイン＋匿名/現職ブロック。目的はカニバリ防止ではなく、同意とバレ防止。

### ファネル

#### Stage 1: 獲得

メディアとイベントから流入させる。振り分けの原則は「温度 × その瞬間にかけられる手間」。

- 高意欲、またはじっくり入力できる場面（HP・イベント申込・案件クリック）→ CodeCast の会員登録へ直行
- 低意欲、または一瞬しか取れない場面（YouTube の受動視聴・ブース通りすがり）→ LINE 友だち追加 → ナーチャ → CodeCast へ

温度が混在するチャネル（YouTube・X）では、2枚の CTA を出して本人に選ばせる。

メディアは2系統で補完する。YouTube（Inside the Code）で業界の世界観を作り、CA の X で「人」を見せる。YouTube は職種横断の密着・インタビューと、経営者・CTO・VPoE 等のキーパーソン。X は職種ごとにアイコン CA を1〜2名立てる。

イベントは3系統を深さで使い分ける。食事会（5〜10名・週1〜隔週）は候補者とキーパーソンの獲得を兼ね、当日 CA が取材して検証まで済ませる。自社主催（30〜100名・月1〜隔月）は有名登壇者で集め、その登壇者は食事会経由で確保する。スポンサー出展は最大規模・最低温度で、唯一 LINE 先行（QR＋ノベルティ）にする。申込・参加管理はすべて CodeCast で行う。

#### Stage 2: 意欲判定と振り分け

意欲は本人の自己申告で取る。複雑なスコアリングはしない。転職意欲と副業意欲は別軸で持つ。

| | 選択肢 | 振り分け |
|---|---|---|
| L4 | 積極的に検討中 | CA が即アプローチ（電話等）→ 面談 |
| L3 | 検討している | CA が即アプローチ → 面談 |
| L2 | よい案件があれば | LINE ナーチャ、いいね対象に含める |
| L1 | 全く考えてない | LINE ナーチャ、定期的に再確認 |

意欲は登録直後に取る。アカウント作成の摩擦を下げるため最初の入力項目は最小限にするが、意欲の取得が後ろにずれると、登録済みでプロフィール未入力の L4 が検知されないまま滞留する。ここが最大の漏れ口になる。

L1〜L2 もいいね対象には含める（オプトイン済みの場合）。企業からのいいねが、温度を上げる最も強いトリガーになる。

意欲は継続更新する。月1アンケート、プロフィール更新の常設、配信内 CTA の「相談したい」は即 L4 扱い、いいかも返し・スカウト返信は L3 以上に引き上げる。

#### Stage 3: 刈り取り

入口は2つ。①企業のいいね → マッチング → スカウト → 返信、②CA の即アプローチ／Slack トスアップ。どちらも初回面談（オンライン30分）に合流する。

初回面談のゴールは4つ。ニーズを引き出して自社の強みに繋ぐ、プロフィールを取材検証して完成させる（＝検証済み在庫化）、担当 CA の公式LINE を交換する、転職/副業の方向性に合意する。

やり取りの境界は「CodeCast でできるか」ではなく「CodeCast だと間に合うか」。通常の提案・履歴・稼働報告は CodeCast に留め、本命案件の一押し、日程の直前リマインド、意思決定の山場、離脱者の復帰といった「落とすと損失が大きい」局面だけ LINE で起こす。プッシュを乱発すると即レスレールとしての価値が落ちる。

クロージングは「めんどくさい全部やる」。書類作成、日程調整、辞退・内定連絡、年収交渉、入社・退職サポートまで代行し、CodeCast 上のチェックリストで管理する。これが 35% の中身になる。

副業は稼働報告・案件・報酬・契約を CodeCast で管理する（常時アクティブの核であり、稼働 MRR の可視化でもある）。成約後は入社後カウンセリング、昇給支援、副業紹介、次の転職での再活用へ繋ぐ。

### KPI

すべて職種別に分解する。

| 段階 | 中核KPI | 補助指標 |
|---|---|---|
| Stage 1 獲得 | チャネル別の CodeCast 登録数 | 再生/フォロワー→登録率、LINE→CodeCast 登録率、イベント参加→登録率 |
| Stage 2 判定 | 月次面談設定数 | L1〜L4 の在庫（転職/副業別）、登録→面談日数、プロフィール完成率、LINE 連携率 |
