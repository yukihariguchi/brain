# Hello（パーソナルアシスタント）

Hello が出す汎用パーソナルアシスタント。サービス名は Hello（2026-09-24 決定）。HelloDining とは別の新サービスとして考える。
前半は「他のプレイヤーにどう勝つか」、後半は決めた仕様（代理電話・決済）。法人・体制は hello/base.md。

## 取る位置（2026-09-24）

- 相手が API も Web も持たない現実世界（店・病院・業者・役所）に、電話で届く。検索エンジンもエージェントも届かない領域で、電話をかけるコストが下がった瞬間に開く
- 予約だけでなく「今の状態を聞く」（行列・空席・在庫・見積もり）、比べる（3 軒に同時に聞く）、手続き（変更・再配達・保留待ち）、受ける（折り返し・宅配・営業電話の遮断）
- 会話の場（LINE・Instagram・OS）は取らない。取るのは「決めた後の実行」と「電話の窓口」

## なぜ Hello が勝てるか

他社との差は「本人が電話の中に居られる」ことと、HelloX と HelloPay の掛け合わせ。

- Apple・Google: 本人の携帯番号への着信を端末の中で受け、用件を文字にするまで（Pixel の Call Screen は 2018 年から、iOS 26 は日本語対応）。Hello は Hello の番号を網の側で受け、受けた後に予約や変更まで動く。Google は Duplex・Call Screen・Pixel と部品を全部持つので、優位の寿命は 12〜24 か月と見る
- Meta Muse: 電話を人のコールセンターに隠れてやらせて叩かれた（2026-09）。米国限定・英語のみ。Hello は「本人が出る」を正面から製品にする
- LINE ヤフー Agent i: トークルームの中。Hello はそこと競わず、電話と実行を取る

Hello にしかできない 3 つ（HelloX × HelloPay）

1. カード保証つきの予約電話: 無断キャンセル時にデポジットが取れる予約として店に伝えられる。店が AI の電話を受ける理由になる
2. 電話で交渉して、その場で払う: 見積もり → 交渉 → 支払いまで 1 本の電話で終わる。Web も API も無い相手に決済まで届く
3. 相手も HelloX なら音声でなくデータで済む: HelloX 導入先が増えるほど Hello の完了率が上がり、日本語の音声 AI の精度問題を飛ばせる

## 早い者勝ちが成立する条件

パーソナルアシスタントは一度選ぶと変えにくい。ただし残るのは切替費用が積まれた分だけ。取った数より、1 人あたりに積まれた量が守りの厚さ。

- 積まれるもの: 本人が外に出した Hello の番号（店・病院・宅配の連絡先に入る）/ 記録（どこに何を頼み、何と言われたか）/ 保存済みのログインセッションとカード / 委任の設定
- 積まれないもの: チャット画面、モデルの賢さ、実況の UI。相手が同じ物を出せば差が消える
- テスター版から「番号を外に出す」「記録を残す」は落とさない

## 重要な決定（詳細は後半）

- 引き継ぎは本人がやる。運用部隊は Hello には使わない。本人が出なければ「折り返します」と言って切る（2026-09-24）
- 決済は本人のカード。HelloPay の PCI DSS で番号を保管し、毎回本人が打つのは CVV と本人認証だけ。認証画面はエージェントのブラウザを本人の端末に映す Live View で本人が打つ。コードを Hello に転送させない（2026-09-24）
- 電話番号はプール方式から。1 人 1 本は数字を見て切り替える。SMS は使わない（2026-09-24）
- Web 操作は AI が手順を作りコードが実行する。AI に毎回操作させない。LLM は 3 層（判断は上位、量は安価、音声は HelloX）で切り替え可能にする（2026-09-24）

## やらないこと

- 自前のチャットや連絡先で LINE を置き換えに行く（会話の場は取らない）
- 運用部隊で電話を引き取る
- 自前の LLM
- 電話でカード番号を読み上げる、ワンタイムコードを Hello に送らせる

## 測る数字

- 90 日後に残っている率 / 1 ユーザーあたりの積み上げ（外に出した番号の使用回数・記録の件数・保存セッション数）
- 依頼から確定までの中央値 / 本人の介入なしで確定した率 / 店が電話を切った率 / 「確定」と表示して予約が無かった率

## 議論中（未決）

- 課金（番号・月額・件数）
- 優位の 12〜24 か月で何をどの順に積むか

## 代理電話（2026-09-24 決定）

### 引き継ぎは本人がやる。運用部隊は使わない

- AI が続けられない場面（店が本人を求めた / 答えを持たない質問 / 同じ聞き返し 2 回 / 譲れる幅の外の提案 / 口頭でカード番号を求められた）で、AI は店に「少々お待ちください。ご本人が出られるか確認しております」と言い、本人に着信音つきの全画面通知を出す
- 待ち時間は 30 秒（仮置き）。15 秒で店に「もう少々お待ちください」と一言。店の許容はテスター版で測って直す
- 本人が出た: 「お待たせしました。ご本人に代わります」と言って本人の回線を開く。AI は切らずに聞き続けて記録を続け、「AI に戻す」で再開する
- 出なかった: 「確認が取れませんでしたので、改めてこちらからお電話いたします」と言って切る。結果は「未確定・折り返し待ち」。本人が通知を開いた時点で「今なら出られますか」と聞き、出られれば即再発信、出られなければ時間を選ばせて予約発信。再発信では「先ほどお電話した Hello です」と続きから話す
- 予防: 発信前に「今から 10 分ほど通知に出られますか」と聞く。聞かれそうなこと（アレルギー・コース・席・遅刻の可能性）は発信前に本人に答えさせる
- ユーザーの指示は、店の発話が終わった次の AI の番で反映する。嘘・脅し・カード番号などの機微情報は反映せず理由を出す
- 成否の判定はモデルに任せない。店が日時・人数を復唱した、または AI の復唱を店が肯定した発話を必須の証拠にし、無ければ「確定」と表示しない
- 店には冒頭で AI であることと録音を告げる（文言は要確認。AutoReserve の現行の告知に合わせる）

### 電話番号はプール方式から始める

- 1 ユーザー 1 番号は最初はやらない。番号のプールから、同じユーザーには毎回同じ番号を割り当てる（例: 20 ユーザーに 1 本。同じ店に同じ番号が別名でかからないよう割り当てる）
- 1 人 1 本に切り替える条件: 折り返しの誤紐づけ率 / 店側の着信拒否の発生率 / 「同じ番号が別名でかけてくる」と店が指摘した件数、のどれかが目立ったとき。その場合は有料プランの特典として専用番号を出す
- SMS は使わない。日本では 050・03 番号に SMS は付かず、SMS 受信は企業共通の審査済み番号（KDDI メッセージキャスト等）に限られる。店からの確認は Hello 払い出しのメールアドレスと折り返し電話で受ける
- 番号の効用が大きいのは発信でなく着信。本人が外に出す番号（店・病院・宅配の連絡先）になったときに切替費用として積み上がる。テスター版では専用番号 10 本を配り、「本人が外に出す番号として使うか」を観察する

## 決済（2026-09-24 決定）

### 原則

- ユーザー本人のカードを使う。Hello の法人カードやバーチャルカードで立て替えない
  - 店にはユーザー本人の名義が出る。返金・紛争はユーザーと店の間で済む。Hello は資金の流れに入らないので、資金移動業・前払式支払手段・割賦販売法の論点が立たない
- カード番号・CVV・ワンタイムコードを LLM に見せない。入力はコードが行い、モデルには伏せ字だけ渡す。画面の読み取り前に入力欄を隠す
- ワンタイムコードをユーザーから Hello に転送させない（採らない、下記）

### 今すぐ組む形（直接入力。2026-09-24 決定: ユーザーの手間を最小にする）

- 支払い手段の選び方（軽い順。2026-09-24 追記）
  1. ユーザーがそのサイトにアカウントと保存カードを持つ（一休・TableCheck・OMAKASE 等）: 本人のログイン済みセッションで予約し、支払いはサイト側の保存カードで走る。CVV も本人認証も出ないことが多く、Hello はカード情報に触れない。Hello が保管するのはそのサイトのセッション（Cookie）だけで、パスワードは保管しない。初回ログイン（パスワード・ログイン時の認証コード）とセッション切れの再ログインは Live View で本人が打つ
  2. 保存カードが無い: 下記の直接入力（Hello の保管カードをコードで埋め、CVV と本人認証を Live View）
  3. Cookie 引き継ぎが効くサイト: 支払い画面を端末の WebView に移し、Apple Pay・端末の自動入力を使う（「次の形」）
- 承認の関門: 1 のように支払いが自動で走る経路では、最終の送信前にアプリで金額・日時・キャンセル規定を見せて Face ID で承認させる。CVV 入力が承認を兼ねていた役割をこの 1 タップが引き継ぐ。承認した範囲（金額上限・店・日時）を外れる変更は再承認

- 方針: HelloPay が PCI DSS を持っているので、カードは Hello が保管し、ユーザーが毎回打つのは CVV と本人認証だけにする
- 初回: アプリの専用画面（会話とは別の安全なシート）でカードを登録する。番号・有効期限・名義を PCI の範囲で保管する
- 毎回: エージェントが店の支払いフォームまで進め、保管した番号・有効期限・名義をコードで埋める。CVV だけ空のまま Live View で画面を本人に渡し、本人が CVV を打って送信し、続けて出る 3D セキュアも同じ画面で通す。手渡しは 1 回
  - 手間の下限: CVV 3 桁＋認証（アプリ承認なら 1 タップ、コード型なら 6 桁）。リスク判定で認証が出ない取引（3DS 2.0 のフリクションレス）なら CVV 3 桁だけ
  - CVV は保管禁止（カード規約）、本人認証は発行会社側で出るので、Hello 側では消せない。0 入力にできるのは Hello 名義で請求する形（却下）かエージェント用トークン（本命）だけ
- CVV の入力経路はチャットの文面にしない（LLM とチャット履歴、LINE のサーバーを通るため）。基本は Live View の中で店のフォームに本人が直接打つ。Live View が使えない場面（電話予約のデポジットなど）はアプリの専用入力欄（会話ログに残さず PCI 範囲内のサーバーからブラウザへ注入）。LINE だけのユーザーは LIFF の HTTPS フォーム
- 却下した軽い版: カード情報を全部ユーザーが Live View で毎回打つ（Hello は保管しない）。PCI の保管審査は要らないが、Live View は画面のピクセルなので端末のカード自動入力が効かず、毎回 16 桁を手で打つことになる。PCI DSS を持っている以上、採らない
- PCI DSS の範囲: HelloPay の既存の審査で「保管した番号をコードで他社サイトに入力する」まで収まるか要確認

### Live View 方式（3D セキュア・想定外の画面の手渡し）

- エージェントのブラウザは Hello 側（クラウド）で動く。認証画面（カード会社のページ）が出たら、その画面だけを Hello アプリに映し、ユーザーが自分の端末でコードを打つ。Hello はコードを受け取って代理入力するのでなく、本人が入力する経路を運ぶ
- 商用の部品がある（Browserbase の Session Live View、Cloudflare Browser Run の Human in the Loop）。自前なら Chrome DevTools Protocol の画面配信と入力転送で同じ物になる
- 限界: 入力イベントは Hello のサーバーを経由する。「見ない・記録しない」は運用の約束であり、暗号的に見えない訳ではない
- SMS コード型・アプリ承認型のどちらのカードでも同じ体験（通知 1 回・入力 1 回）になる
- 決済の成否はモデルに判定させない。認証画面 → 店のサイトへの戻り遷移をフレーム遷移イベントで検知し、完了ページの予約番号（DOM）と通信の応答を証拠にする。証拠が無ければ「未確定」として人か電話に落とす。失敗時に自動で押し直さない（二重決済の防止）
- 補助の証拠: 予約の連絡先に Hello が払い出したメールアドレスと HelloX の電話番号を使えば、店からの確認メール・SMS・折り返しが Hello に届く。Respo の店は台帳に予約と決済の状態がそのまま立つ
- ユーザーが途中でアプリを閉じてもブラウザは生きている。認証画面のタイムアウト（数分。カード会社ごとに要確認）までは再開できる形にする

### 次の形（効くサイトから順に）

- 決済の一歩だけをユーザーの端末に移す。エージェントが予約内容まで進めたら、サイトのセッション（Cookie）を Hello アプリ内の WebView に引き継ぎ、支払い画面はユーザーが自分の端末で操作する。カード番号・CVV・コードが Hello を一切通らず、PCI DSS の範囲から外れる
- 欠点: セッションを IP や端末に縛るサイトで切れる。Live View を基本にし、引き継ぎが効くサイトから移す

### 本命（エージェント用トークン）

- Visa Intelligent Commerce と Mastercard Agent Pay は、ユーザーのカードを「特定のエージェント・用途・上限」に縛ったトークンにして渡す仕組み。生の番号も CVV も持たず、発行会社が「エージェントの取引」と分かる
- 状況（2026-09-24 時点）: Mastercard は 2025-11 に米国の全会員が対象、以後グローバル展開。Visa は 2026 年初頭からアジア太平洋で試験導入（規制と体制が整い次第。日本の明記なし）。国内では GMO ペイメントゲートウェイが 2026-02 に Visa のネットワークトークン決済を実装。日本の発行会社の対応は要確認
- Hello は両プログラムにエージェントとして登録申請し、発行会社の対応が来た時点で直接入力からトークンに切り替える

### 採らない案と理由

- Hello の法人バーチャルカード（インフキュリオン Xard 等で 1 件ごとに発行）で立て替え、HelloPay でユーザーに請求する: 仕組みは日本にあるが、店に Hello 名義が出る、Hello が両側のチャージバックを負う、立替の法的整理が要る。ユーザー本人のカードを使う方針と合わない
- ユーザーごとの使い捨てカードを第三者 API で発行（Muse 型）: 日本に個人向けの発行基盤が見当たらない
- ワンタイムコードをユーザーから Hello へ転送させる（自己責任）: ユーザーの補償が消えるだけでなく、カード会社が「他人に教えるな」と教育している行為をサービスが求める形になる。詐欺師が同じ文面を使え、事故時に Hello の名前で報じられる。Live View 方式で同じ手間の体験が出るので採る理由がない

### 要確認

- HelloPay の PCI DSS の範囲で、カード番号の保管と代理入力が追加審査なしで収まるか
- カード会社ごとの 3D セキュアの方式（アプリ承認・SMS コード）と認証画面のタイムアウト
- Visa Intelligent Commerce / Mastercard Agent Pay の日本の発行会社の対応時期と、エージェント登録の要件
- 主要な予約サイトで Cookie 引き継ぎが効くか（サイトごとに実測）
