# HelloPay

Hello の決済代行。法人・体制は hello/base.md。ここには、Hello（パーソナルアシスタント）や AutoReserve がユーザーの代わりに払う仕組みを置く。

## 事実（2026-09-25）

- 決済代行（PSP）。カード・Apple Pay・Google Pay・サブスク決済を API で提供。PCI DSS あり
- アクワイアラーからの入金は月 6 回（5 日締め）
- カード発行のライセンスは持たない。発行はライフカードを BIN スポンサーにする（2026-09-25 決定。経緯は decisions.md）

## 仕組み: 店によって 2 つの道

| | C. HelloPay 加盟店 | A. それ以外の店 |
|---|---|---|
| どう払うか | 保管してあるユーザーのカードで、API で店に請求 | ライフカードが「この 1 回だけの番号」を出し、エージェントが店の入力欄に打つ |
| 間に入るもの | HelloPay だけ | HelloPay → ライフカード |
| 立て替え | なし | あり |
| ユーザーの明細 | 店の名前。ポイントも付く | 「HELLOPAY」。店名はアプリ内でだけ見える |
| 店から見えるもの | 普通のカード決済 | 使い切りの Visa プリペイド。名前欄は本人名か「HELLO MEMBER」（本人名を入れられるかは要確認） |

Stripe の Link も同じ分け方（Link 対応店は直接、それ以外は使い切りカード）。

A の流れ

1. ユーザーは最初に 1 度だけ Hello にクレカを登録する。本人認証はこの時だけ
2. エージェントが払う直前に止まり、チャットで「店と金額」の OK をもらう
3. HelloPay が登録カードに請求し、ライフカードが承認額を上限にした使い切り番号を数秒で出す
4. エージェントが番号を店に打つ。店が本人認証を求めたら、ライフカードが Hello の承認記録を根拠に通す
5. 買えたら完了。買えなければ番号は消え、請求は戻る

役割: ライフカードは発行ライセンス・前払式支払手段の登録・店への支払い。Hello は商品設計・カード保管と請求・承認画面・帳簿・損失（不正・誤購入・チャージバック）。

お金: Hello から出るのは、使い切り番号に入れる金額をライフカードに渡す時。保証金のプールを置いて発行のたびに引かれる形が有力。目安は月の決済額の 20% 前後（5 日ごとに補充）。

## 1 件あたりの損益（1 万円。数字は推測。実料率で引き直す）

| | A. クレカ裏付け | B. 銀行口座裏付け | C. 加盟店 |
|---|---|---|---|
| ユーザーから集める手数料 | −200 円（2.0%。プリペイドチャージ扱いで上がる可能性） | −30 円 | 0 円 |
| 発行手数料（バーチャル） | −10〜30 円 | −10〜30 円 | 0 円 |
| インターチェンジの分配 | +80 円（要交渉） | +80 円 | 0 円 |
| 加盟店手数料 − アクワイアラー原価 | 0 円 | 0 円 | +100 円（3.2% − 2.2%） |
| 不正・誤購入の引当 | −20 円 | −20 円 | 通常の PSP と同じ |
| 合計 | −150〜−170 円 | ほぼ 0 円 | +100 円 |

- 黒字は C だけ。全体の損益は決済額のうち C の割合で決まる
- 入口は A（登録が軽い）。弱点はカード会社に「プリペイドチャージ」と見えてポイント対象外・拒否が起きうること。B は集める手数料を抑えたい人向けに後ろに置く
- 稼ぐ場所: 月額・件数課金（A の赤字を織り込む）/ C の利ざや / 予約デポジットと店側の成果報酬

## ロードマップ

- 段階 0（2026-10〜11）: ライフカードと決める。取引ごとに出す API と速度 / 名前欄 / 本人認証の判定を Hello の承認記録に任せられるか / 損失の分担と上限 / 手数料の分け方 / プールの形と最低残高。弁護士確認: 即時チャージが前払式のままか、本人確認の要否、外部エージェントを「ユーザーの代理人」として扱う規約。カード会社ごとのプリペイドチャージの扱い。出口は条件書
- 段階 1（2026-12〜2027-02）: 最小構成。カード保管・請求・返金の帳簿・ライフカード接続・承認画面。社内 100 件で誤請求ゼロ
- 段階 2（2027-03〜05）: テスター公開。電話の先の決済（決済リンク・電話での番号伝達・予約デポジット）。返金・紛争の運用。銀行口座チャージ
- 段階 3（2027 年後半）: トークン方式。対応発行会社のカードは直接払い、使い切りカードは残りの店だけ

Live View 方式（本人のカードをエージェントが打ち、CVV と認証を本人が打つ。hello/hello.md）は予備。

## トークン方式（段階 3）

Visa Intelligent Commerce / Mastercard Agent Pay。ユーザーの既存カードに Hello 専用の別番号を紐づける（Apple Pay の端末専用番号と同じ考え方）。

- 通すかはユーザーのカードの発行会社が決める。Visa・Mastercard が対応しても、発行会社が未対応なら使えない
- Hello はお金の流れに入らない。立て替え・損失・前払式の登録が不要。収入も 0

## 外部への提供（方針）

AutoReserve・Hello・外部サービスが同じ「HelloPay の財布」API を使う。ユーザーは Hello ID で 1 回登録すれば、どのエージェントからも使える。

- 契約: ユーザー ⇄ HelloPay・ライフカード / エージェント ⇄ HelloPay（代理の規約。誤購入はエージェント負担）。外部はライフカードと直接契約しない
- 審査: 外部エージェントは加盟店ではなく「ユーザーの代理人」。法人・反社・用途・承認画面・上限・業種を HelloPay とライフカードが審査する。加盟店審査を受けるのは HelloPay 自身
- カード番号は外部に渡さない。HelloPay 側のブラウザ部品が店のフォームに打つ（渡すと外部が PCI DSS の対象になる）
- 稼ぎ方: 社内は原価。外部は取引ごとに 3% 前後（上限 3.5%）。A の原価を引いて 1.3〜1.5% が残る。外部が HelloPay 加盟店で払う時は手数料を 0〜1% に下げ、加盟店に流す動機にする（加盟店側の利ざや +1% が別に残る）。外販は財布の登録者が先
- 先に潰す論点: ライフカードの契約に「外販あり」を最初から入れる（外部を Hello の下のプログラムとして 1 社ずつ認める形。UPSIDER が法人カード基盤を白ラベルで外部提供している前例があるので通る見込み。ただし消費者向け・代理人が使う点が違うので条件は付く）/ 承認画面は HelloPay 側で出す（外部の画面に任せると偽の同意を作れる。外部のユーザーも Hello ID を持つ）/ 誤購入は HelloPay が先に返金し外部から取り返す。保証金か手数料の相殺を契約に入れる / カード番号を外部に渡すと PCI DSS の範囲に入る。渡す場合は QSA に確認

## 加盟店を増やす（方針）

- 店が動くのは客の流れが見えた時。差は「払う・予約する」の瞬間にだけ出す（決済が確実に通る・無断キャンセルの保証・返金がチャットで済む）。店選びの順位では優遇しない（hello-dining.md）
- 気づかせる: 失敗した店にだけ通知 / 電話予約で「カード保証つきで受けられますか」と聞く / Respo・HelloX の管理画面に件数を出す
- 順番: 既存の PSP はそのまま Hello 用の受け口を 1 本足す → Hello 経由の比率を上げる → 2〜3 割で乗り換え。受け口は共通規格（UCP・ACP）で
- この仕組みだけで乗り換えは起きない。料率が下がるのも Visa を通さない閉じた残高（PayPay 型）だけ

## Hello カード（先の段。未決）

自社カードを Hello の既定の支払い手段にして、A の赤字を反転させる案。集客の道具ではなく損益を直す道具。

- 効く理由: 集める手数料 2% が消え、外の買い物でもインターチェンジが入る。−1.5% が +1% 前後になり、ポイントの原資が出る
- 形: まず与信なし（銀行口座から入れるデビット・プリペイド型）。クレジット化は利用額が育ってから
- 反論: 差は発行会社 3 社がトークン対応を出せば消える（12〜18 か月）/ 日本のカード獲得はポイント競争（Kyash が実例）

## 他社と業界（2026-09-25）

- 収束点: エージェントにカード番号を渡さず、トークンか使い捨ての権限を使い、本人はパスキーかウォレットで承認
- 海外: Visa・Mastercard・Amex がエージェント用トークン。Stripe Link（Muse が採用）・PayPal・Shop Pay は財布側。OpenAI のチャット内決済は 2026-03 に終了。Stripe のエージェント用の仕組みは日本非対応
- 日本: 本番は 2026-05-20 の Mastercard × 三菱UFJニコス × Evonet の 1 件のみ。Visa の検証に三井住友カード・三菱UFJニコス・クレディセゾンが参加。消費者向けに取引ごとの番号を API で出す事業者は無い。法規制にエージェント起点の取引の規定は無い
- 未決着: 誤購入の責任分担 / 本人認証と無人購入の両立
