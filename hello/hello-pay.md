# HelloPay

Hello の決済代行。法人・体制は hello/base.md。ここには HelloPay の立て付けと、Hello（パーソナルアシスタント）がユーザーの代わりに払う仕組みを置く。

## 事実（2026-09-25）

- 決済代行（PSP）。カード・Apple Pay・Google Pay・サブスク決済を API で提供。PCI DSS あり（審査範囲は要確認）
- アクワイアラーからの入金は月 6 回（5 日締め）。締めから入金までの日数は要確認
- カード発行のライセンスは持たない

## エージェント決済の全体像（2026-09-25 決定。経緯は decisions.md）

店が HelloPay 加盟店かどうかで、2 つに分かれる。

- HelloPay 加盟店: 使い切りカードは要らない。店の決済処理を HelloPay が動かしているので、保管してあるユーザーのカードで「この店にこの額」と API で請求するだけ。番号をどこにも打たず、ライフカードも立て替えも入らない
- それ以外の店: 店の入力欄に何かのカード番号を打つしかない。ユーザーの本当の番号は打ちたくないので、ライフカードに「この 1 回だけの番号」を出してもらう（下記）

Stripe の Link も同じ分け方。Link 対応店は Stripe が直接処理し、それ以外の店で使い切りカードを出す。

## 使い切りカード方式（ライフカードが BIN スポンサー）

ライフカードが Visa の発行ライセンスを持ち、Hello の商品を載せる。ライフカードは消費者向けの使い切りバーチャル Visa プリペイド（Vプリカ。3D セキュア 2.0 対応）を既に運営している。

1 回の流れ

1. ユーザーは最初に 1 度だけ、Hello アプリにクレカを登録する。本人認証はこの時だけ
2. エージェントが決済の直前で止まり、チャットで「店と金額」の承認を求める
3. ユーザーが OK を押す
4. HelloPay が登録カードに請求する（2 回目以降は認証なしの継続課金）
5. ライフカードが、承認額を上限にした本人名義の使い切り番号を数秒で出す
6. エージェントがその番号を店に打つ
7. 店が本人認証を求めたら、発行元のライフカードが Hello の承認記録を根拠に通す。ユーザーは何もしない
8. 買えたら完了。買えなければ番号は消え、請求は戻る

役割分担

- ライフカード: 発行ライセンス、前払式支払手段の登録、店への支払い（Visa 経由）
- Hello: 商品設計、カード保管と請求、承認画面、帳簿、不正・誤購入・チャージバックの損失
- 店にはユーザーのカード番号も Hello 名義も出ない

お金の出入り

- Hello から出るのは、使い切り番号に入れる金額をライフカードに渡す時。前払式なので、Hello が保証金のプールを置いて発行のたびに引かれる形が有力（後精算は要交渉）
- プールの目安は「補充の間隔分の決済額＋余裕」。5 日ごとの補充なら月の決済額の 20% 前後。返金はプールに戻る
- クレカに請求したお金が Hello に入るまでは、入金が月 6 回なので平均 7〜8 日

## 1 件あたりの損益（1 万円の取引。数字は推測。HelloPay の実料率で引き直す）

| | A. クレカ裏付け | B. 銀行口座裏付け | C. HelloPay 加盟店 |
|---|---|---|---|
| 使う場面 | 加盟店以外（既定） | 加盟店以外。集める手数料を抑えたい人向け | HelloPay 加盟店 |
| お金の流れ | クレカ → HelloPay → ライフカード → 店 | 銀行口座 → HelloPay → ライフカード → 店 | クレカ → 店（HelloPay が間に立つ） |
| ユーザーから集める手数料（Hello が店の立場で払う加盟店手数料） | −200 円（料率 2.0%。プリペイドチャージ扱いで上がる可能性、要確認） | −30 円 | 0 円 |
| 発行手数料 | −10〜30 円（バーチャルのみ。米国 Stripe Issuing は 1 枚 0.10 ドル） | −10〜30 円 | 0 円 |
| インターチェンジの分配 | +80 円（店が払う 1.6% の半分、要交渉） | +80 円 | 0 円 |
| 加盟店手数料 | 0 円 | 0 円 | +320 円（3.2% と仮定） |
| アクワイアラー原価 | 0 円 | 0 円 | −220 円（2.2% と仮定） |
| 不正・誤購入の引当 | −20 円 | −20 円 | 通常の PSP と同じ |
| 合計 | −150〜−170 円 | ほぼ 0 円 | +100 円 |
| 立て替え | あり | あり | なし |
| ユーザー側 | 登録が軽い。ポイント対象外・請求拒否の恐れ | 口座連携で離脱が出る | 店名が明細に出てポイントも付く |

- 決済単体で黒字なのは C だけ。全体の損益は、決済額のうち C に流れる割合で決まる
- 入口は A。B は後ろに置く。A の弱点（ポイント・拒否）はトークン方式で消える
- A の赤字の主因はユーザーから集める手数料。縮めるレバーは、アクワイアラー料率とインターチェンジの分け方
- 稼ぐ場所は 3 つ: 月額・件数課金（A の赤字を織り込む）/ C の利ざや / 電話予約のデポジットと店側の成果報酬

## トークン方式（段階 3。Visa Intelligent Commerce / Mastercard Agent Pay）

- ユーザーの既存カードに Hello 専用の別番号を紐づける。Apple Pay の端末専用番号と同じ考え方
- 承認と請求は発行会社がやる。Visa・Mastercard が対応しても、ユーザーのカードの発行会社が対応していないと使えない
- 店側の決済代行がトークン決済を受けられることが条件。Visa と Mastercard は別接続
- Hello はお金の流れに入らない。立て替え・チャージバック・前払式の登録が不要。Hello の収入も 0

## ロードマップ

- 段階 0（2026-10〜11）: ライフカードと 6 つを決める。取引ごとに出す API の有無 / 発行速度 / 本人認証の判定を Hello の承認記録に任せられるか / 損失の分担と上限 / 手数料の分け方 / プールの形と最低残高。並行して弁護士確認（即時チャージが前払式のままか、本人確認の要否、外部エージェントを「ユーザーの代理人」として扱う規約の枠）と、カード会社ごとのプリペイドチャージの扱い（ポイント・拒否）。出口は条件書
- 段階 1（2026-12〜2027-02）: 最小構成。カード保管・請求・返金の帳簿・ライフカード接続・承認画面。エージェント側は番号を打って完了を確認。出口は社内 100 件で誤請求ゼロ
- 段階 2（2027-03〜05）: テスター公開。電話の先の決済（決済リンク、電話での番号伝達、予約デポジット）。返金・紛争の運用。銀行口座チャージ
- 段階 3（2027 年後半）: トークン方式に入る。対応発行会社のカードは直接払い、使い切りカードは残りの店だけ

Live View 方式（本人のカードをエージェントが打ち、CVV と認証を本人が打つ。hello/hello.md）は、上の仕組みが使えない店の予備。

## 加盟店を増やす仕組み（方針。2026-09-25）

店が動く理由は決済手数料でなく客の流れ。Hello 経由の注文が店の売上の数% になった時に初めて動く。

- 差が出る場所は「払う・予約する」の瞬間だけ。加盟店は決済が確実に通り、無断キャンセルの保証が付き、返金がチャットで済む。加盟店以外は「本人確認が要ります」「保証なし」になる
- 店選びの順位で加盟店を優遇しない（hello-dining.md「店選びに金を入れない」と衝突し、AR の精度を壊す）
- 気づかせる方法: 決済や予約が失敗した店にだけ通知を送る（「今月 3 名が支払いを試み、2 件が完了できませんでした」）/ 電話予約で AI が「カード保証つきで受けられますか」と聞く / Respo・HelloX の管理画面に Hello 経由の件数を出す
- 順番: 既存の PSP はそのままに Hello 用の受け口を 1 本足させる → Hello 経由の比率を上げる → 比率が 2〜3 割になった店で乗り換えを取る。受け口は共通規格（UCP・ACP）で作り、「1 回の接続で全エージェント対応」と言えるようにする
- この仕組みだけで PSP を乗り換えさせる方法は無い。乗り換えは規模・料率・運営の束（Respo・HelloX）でしか起きない
- 「発行もやっているから加盟店を安くできる」は成り立たない。加盟店での決済は使い切りカードを出さないので発行側の取り分が無い。料率が本当に下がるのは Visa を通さない閉じた残高（銀行口座から入れ、店へは内部で付け替える。PayPay と同じ）だけ

## Hello カード（先の段。未決、2026-09-25）

自社のカードを Hello の既定の支払い手段にして、決済の損益を反転させる案。人を集める道具ではなく、損益を直す道具として置く。

- 効く理由: A の取引が全部「自社カードで払う」に変わり、ユーザーのクレカから集める 2% が消える。Hello の外の買い物でもインターチェンジが入る。−1.5% が +1% 前後に反転し、ポイントの原資が出る。エージェント用トークンを通すかは発行会社が決めるので、自社カードなら最初から通せる
- 形: まず与信なし（銀行口座から入れるデビット・プリペイド型。段階 2 の銀行口座チャージの延長）。外でも使える。クレジット化は利用額が育ってから、ライフカードと組んで判断（与信と月次の立て替えが要る。使い切りカードのプールより桁が 1 つ大きい）
- 反論: 「Hello で使える」の差は、三井住友・ニコス・セゾンがトークン対応を出せば消える（12〜18 か月と見る）/ 日本のカード獲得はポイント競争で、機能の良さで人が作った例は少ない（Kyash が実例）

## 外部への提供（方針。2026-09-25）

AutoReserve・Hello・外部サービスが同じ「HelloPay の財布」API を使う。ユーザーは Hello ID で 1 回登録すれば、どのエージェントからも使える。

- 契約: ユーザー ⇄ HelloPay・ライフカード（カードの規約）/ エージェント ⇄ HelloPay（代理の規約。誤購入はエージェント負担）/ HelloPay ⇄ ライフカード。外部はライフカードと直接契約しない
- カード番号は外部に渡さない。HelloPay 側のブラウザ部品が店のフォームに打つ。渡すと外部が PCI DSS の対象になる
- 審査: 外部エージェントは加盟店ではなく「ユーザーの代理人」。HelloPay とライフカードが、法人・反社・用途・承認画面の実装・上限・業種の範囲を審査する。加盟店審査を受けるのは HelloPay 自身（プリペイドチャージの業種）。段階 3 では Visa・Mastercard へのエージェント登録が別に要る
- 明細は 2 段。ユーザーのクレカ明細は「HELLOPAY」名義で店名は出ない（動的表記「HELLO*店名」の可否は要確認）。店側はユーザー本人名義の Visa プリペイド。店名はアプリ内の明細でしか見えないので、アプリ内の明細と返金手順を先に作る
- 稼ぎ方: 社内（AutoReserve・Hello）は原価。外部には A の原価を上回る取引ごとの手数料。財布はサービス横断で共通にし、登録者数を資産にする。外販は財布の登録者が先で、Hello と AutoReserve で数を作ってから

## 他社と業界（2026-09-25 時点）

- 収束点: エージェントにカード番号を渡さない。ネットワークトークンか使い捨ての権限を使い、本人はパスキーかウォレットで承認
- カード会社系: Visa Intelligent Commerce、Mastercard Agent Pay（米国展開済み、SG で本番）、Amex ACE（誤購入を補償）
- 財布系: Stripe Link（Meta Muse が採用）、PayPal、Shop Pay、Google Pay。Stripe のエージェント用の仕組みは日本非対応
- 加盟店側: OpenAI ACP、Google UCP、Adyen Agentic。OpenAI のチャット内決済は 2026-03 に終了
- 未決着: 誤購入の責任分担 / 本人認証と無人購入の両立 / 国またぎ
- 日本: 本番は 2026-05-20 の Mastercard × 三菱UFJニコス × Evonet の 1 件のみ。Visa の検証に三井住友カード・三菱UFJニコス・クレディセゾンが参加（本番は要確認）。GMO-PG は UCP と Visa ネットワークトークンに対応。消費者向けに取引ごとの番号を API で出す事業者は無い。Agent i・楽天 AI は決済直前で本人に押させる。法規制にエージェント起点の取引の規定は無い
