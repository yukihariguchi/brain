# Hello（パーソナルアシスタント）

汎用パーソナルアシスタント。プロダクトは Hello、会社は HelloAI（新設する株式会社HelloAI）と呼ぶ（2026-11-18。10-16 の社内呼称 Hello Assistant / HA は廃止。サービス名 Hello は 2026-09-24 決定）。
「他のプレイヤーにどう勝つか」だけを書く。HelloAI の立て付けは reorg.md「全体像」、移す前の体制は hello/base.md。

## 何をするサービスか（2026-09-24）

Muse・ChatGPT・Gemini と同じ種類の汎用パーソナルアシスタント。頼まれた用事を本人の代わりに終わらせる。

- 当たり前にできること（他社と同水準。差にはならないが無いと選ばれない）: 予約サイトを横断して比べて予約する / EC で探して買う / フォームの入力・会員登録・問い合わせ / 旅程や日程の調整 / 記憶（好み・名乗る名前・同行者・過去の依頼）を使って次の依頼を短くする
- 他社より優れているところ（差がつく 2 つ）: 電話と決済。相手が API も Web も持たない現実世界（店・病院・業者・役所）に電話で届き、決済まで本人のカードで完結させる
- チャットと連絡先を Hello の中に持ち、LINE を disrupt する。友人と普通に会話でき、グループチャットもできる。同じ部屋にパーソナルアシスタントが居て用事を引き受ける。人を連れてくる入口は用事（予定・予約・支払い）から生まれる部屋（下記）

## なぜ Hello が勝てるか

当たり前の部分では他社と並ぶ。差がつくのは電話と決済で、どちらもグループの既存資産（HelloX・HelloPay）から出る。

電話（他社は日本に無い・Pixel だけ・後で読む・受けるだけ）

Hello ができること

- Hello がユーザー 1 人 1 人に付与した 050 番号から AI が電話をかける。予約だけでなく、行列や空席や在庫を聞く、見積もりを取る、変更やキャンセルや再配達の手続き、保留や自動音声の待ち
- 本人は通話の文字起こしを実況で見て、途中で自由文で指示できる（「誕生日と伝えて」「20 時でも可」）
- 本人はいつでも自分が出られ、終わったら AI に戻せる。AI が続けられない場面は AI の側から本人を呼ぶ。出られなければ「折り返します」と言って切り、本人が出られる時にかけ直す
- 3 軒に聞くなら順にかけて、答えを表で返す。通話は 1 本ずつで、メイン画面がそのまま通話画面になる（同時に複数の通話を見せない）
- 着信も AI が受ける。店の折り返しは用件を解決し、宅配や業者は用件を文字で渡し、営業電話は切り、大事な電話だけ本人に繋ぐ
- 日英仏伊西独。旅先の店に現地語でかけ、訪日客の代わりに日本語でかける。本人が引き継いだ後も同時通訳が入るので、言葉が通じない相手と本人が直接話せる
- 通話の内容は全部本人の記録に残る（「あの店に何と言われたか」を後で引ける）

他社との差（2026-09-25 更新）

- Google: 2026-09-24 に「Call for Me」を米国の Pixel 11・有料 Gemini 向けに小規模で開始。AI が店に電話し、本人は実況を見て、いつでも引き取れる。発信は本人の携帯番号から。「本人が実況を見て引き取れる発信」自体はもう独自ではない。日本語・Pixel 以外の端末・日本での提供は無い。着信側は Pixel の Call Screen（2018 年〜）が用件を文字にするまで。Google は部品を全部持つので、日本語版が出た時点で残る差は Hello 名義の番号への着信・決済・チャットになる。優位の寿命は 12〜24 か月と置くが推測で、毎月の競合比較で見直す
- Genspark: 2025 年から日本語の代理電話（Call For Me）を日本で提供（有料プラン）。予約・問い合わせ・キャンセルを AI が日本語でかける。ただし本人が電話を引き取る機能が無く、日本語の音声対音声の精度が低いため、ほぼ使われていないと見る（播口の見立て。利用実態は要確認）。「AI が日本語で電話をかける」だけでは使われない、という先例として読む
- Apple: iOS 26 で着信スクリーニングと保留待ちが日本語対応。端末の中で受けて用件を文字にするまで。発信の代行は無い
- Meta Muse: 電話を人のコールセンターに隠れてやらせて叩かれた（2026-09）。米国限定・英語のみ。日本は未定
- LINE ヤフー Agent i: トークルームの中で予約・購入。電話は無い

Hello に残る差は 4 つ。日本語で今出せること / Hello が付与した本人名義の番号で発信し着信も受けること / どの端末でも使えること / 電話の先で決済まで完結すること（HelloPay for Agents）

決済（他社は途中で本人にバトンを渡す。2026-09-25 更新）

- 主方式は HelloPay for Agents（hello/hello-pay.md）。本人は最初に 1 度カードを登録し、以後はチャットで OK を押すだけ。HelloPay 加盟店なら直接請求、それ以外の店はライフカードが出す使い切り番号をエージェントが打つ。本人認証も本人が打たない。Web も API も無い相手（電話の先）にも、その場で決済まで届く
- Live View（エージェントのブラウザを本人の端末に映し、本人が認証を打つ）は 2 つの役割。1 つは、HelloPay for Agents がライフカードとの契約や開発で Hello の公開に間に合わない場合の最初の決済方式（本人のカードを HelloPay の PCI DSS で保管し、コードが埋める。CVC と本人認証のコードはアプリ内のフォームで受ける。2026-11-20）。もう 1 つは、for Agents が動いた後の例外用。プリペイドを弾く店（ホテルの与信枠・レンタカー・一部のサブスク）、決済以外の認証（ログインの 2 段階認証）、発行側の障害時

Live View の仕組みと使う理由（2026-09-27）

- 仕組み: エージェントがクラウドのブラウザで店の決済ページまで進め、本人認証の画面になったら、そのブラウザの映像を Hello アプリに映す。本人は映った画面（店やカード会社のページ）に自分で打つ。打鍵は映像と同じ経路で遠隔ブラウザに届き、Hello のサーバーと LLM は値を持たない。打ち終わったらエージェントが続きを引き取る
- 理由 1（2026-11-20 撤回。本人認証のコードもアプリ内のフォームで受ける。「電話・ブラウザ」）: 本人認証のコードを Hello が受け取らない。アプリに入力欄を出して裏でブラウザに書き込む方式は、値が Hello を通るので「コードの転送」と同じになる。転送はカード会社が禁じ、本人の補償が消え、詐欺の手口と同じ形になる
- 理由 2: 認証画面は相手ごとに違う（コード入力・アプリ承認・パスワード・ログインの 2 段階認証）。画面をそのまま見せれば、どの欄に何を書くかを Hello が理解しなくていい
- 理由 3: Live View は主方式でなく最初の方式と例外用。頻度が低いので、体験より安全と汎用性を優先する
- 制約: 映像配信なのでスクロールはもさつく。対策は、エージェントが入力欄まで進めてから渡し、本人の操作を 1 画面で終わらせること。入力体験を上げるなら、画面は相手のページのまま、アプリの入力欄から打鍵を遠隔ブラウザに直送する（Hello の API と LLM を通さない）
- 発行会社が銀行アプリの承認を使うカードは、本人が自分のアプリで承認するだけで済む。Live View は要らず、エージェントは待って「次へ」を押す

掛け合わせで Hello にしかできない 3 つ（HelloX × HelloPay）

1. カード保証つきの予約電話: 無断キャンセル時にデポジットが取れる予約として店に伝えられる。店が AI の電話を受ける理由になる
2. 電話で交渉して、その場で払う: 見積もり → 交渉 → 支払いまで 1 本の電話で終わる
3. 相手も HelloX なら音声でなくデータで済む: HelloX 導入先が増えるほど Hello の完了率が上がり、日本語の音声 AI の精度問題を飛ばせる

## 連絡先とチャット: Hello の中のチャットで LINE を disrupt する（2026-09-24 決定）

チャットはシンプルな普通のチャット。友人と 1 対 1 でもグループでも、そのまま会話できる。同じ部屋にそれぞれのパーソナルアシスタントも居て、用事を引き受ける。アシスタントが部屋で喋るのは、本人が承認した時と @Hello で呼ばれた時だけ。それ以外は本人にだけ話す。

チャットを持っている側は、用事の入口と人の関係を握る。LINE がこれを持っている限り、Hello の予約や電話は LINE の会話の下請けになる。だからチャットは後回しにせず、早めに引き剥がしに行く。

LINE は人が先に友だちになって部屋ができる。Hello は用事が先にあり、答えた瞬間に部屋ができる。部屋にはアシスタントが居るので、人が黙っても部屋は死なない。

- 部屋は相手ごと。参加者は人と、それぞれのアシスタント（私・相手・私の Hello・相手の Hello）。予定はその部屋の中のカードで、集まりは参加者全員の部屋
- アシスタント同士が日程・条件・支払いを詰める。部屋には確定した事実だけが 1 行で残り、本人向けの文と質問は Hello タブに届き、過程は見せない（2026-09-27。当初は折りたたみで開ける設計だった）。自動で決める範囲は本人の委任ルール 3 つ（曜日と時間帯・予算・食の制約）。外れたら本人に聞く
- 「友達に送って」は Hello 同士なら直接届く。LINE・Instagram の API の制約（第三者は送れない・読めない）を、相手を Hello に連れてくることで越える
- 連絡先は取り込まない。用事を一緒にした人が積まれて名簿になる。Hello 同士はユーザー名で追加できる

バイラルの入口は共有 URL。質問でなく招待として見せる

- 「○○さんがあなたと金曜か土曜に恵比寿で食事をしようとしています」を○○さんのアシスタントが語り、入っている人の名前を見せ、「Hello に入って続ける」の 1 ボタン。押すと 1 タップサインイン → インストール → 同じアカウントで開くと予定と自分のアシスタントが待っている
- 仕組みは 1 つ。URL の裏は「誰から・文脈・目的・範囲」の 4 つだけで、集まり・確定した予約の共有・日程調整・電話で聞いた結果・割り勘まで全部同じ形で通す。カードの予告と最初の一言だけ文脈から自動で変わる
- 電話で聞いた結果の共有（「今聞いてきました: 待ち 20 分」）は Hello にしか無い招待になる
- URL の期限は文脈で自動（予定はその日時まで、電話の結果は 24 時間）。切れても誰から何の話かは見せ、新しい会話に繋ぐ
- リンクの検知はアカウントで行い、端末の推定（deferred deep link）に頼らない。Web で 1 タップサインイン → アプリで開く（Universal Link）→ 同じアカウント、で続きが出る
- 入らない人は幹事のアシスタントが代弁する。幹事は LINE で聞いた答えを一言で伝えるだけ。登録なしで答える経路は最初は出さない。幹事が離れ始めたと数字で見えたら出す

## 早い者勝ちが成立する条件

パーソナルアシスタントは一度選ぶと変えにくい。だから日本では一番最初に出す。「最初」は「AI が電話をかける」ことでなく、実況・途中の指示・本人の引き取り・本人名義の番号・決済まで揃えた形で最初、という意味（AI が電話をかけるだけなら Genspark が先にあり、使われていない）。機能の差でユーザーが乗り換えることもあるが、シンプルに早く出した方がユーザーがつく。Muse・Agent i・Google が日本で使える形になる前に、Hello を選んだ人を作る。

残るのは切替費用が積まれた分だけ。取った数より、1 人あたりに積まれた量が守りの厚さ。

- 積まれるもの: 本人が外に出した Hello の番号とメールアドレス（店・病院・宅配の連絡先に入る。2026-09-27 メールを追加）/ 記録（どこに何を頼み、何と言われたか）/ 保存済みのログインセッションとカード / 委任の設定
- 積まれないもの: チャット画面、モデルの賢さ、実況の UI。相手が同じ物を出せば差が消える
- テスター版から「番号を外に出す」「記録を残す」は落とさない

## 重要な決定（2026-09-24）

- 代理電話の引き継ぎは本人がやる。運用部隊は Hello には使わない。AI が続けられない場面は店に「本人が出られるか確認中」と伝えて待ち、本人が出なければ「折り返します」と言って切る
- 電話番号は 1 ユーザー 1 番号を付与する。050 は SMS 非対応なので、まず電話（発信・着信）から。SMS は後で。日本で電話番号を付与するには本人確認が要るので、電話機能を使う時に本人確認を求める（チャットや招待は本人確認なしで使える）
- 外部サービス（カレンダー・メール・Notion・Slack など）との連携は MCP（Model Context Protocol）で道具として繋ぐ。ユーザー側の許可は各サービスの OAuth
- 2026-09-27 決定: 本人と共有のメールアドレスを Hello が付与する（番号と同じ考え方）。名義は本人、AI が送受信し、本人はいつでも自分で読み書きできる。アカウント作成・予約確認・店や業者への連絡・催促に AI が使う。着信と同じく AI が受けて用件を解決し、大事なものだけ本人に上げる。番号と違い本人確認が要らないので登録直後に配れ、番号が出しにくい国でも同じ構造を保てる。Gmail 等の既存メールは初期から接続し、Hello アドレスと同じ扱いで AI が読み、返信は届いたアドレスから本人として書く（Gmail の受信読み取りに Google の CASA 審査が要るので日程の先頭に置く）。初期リリースには含めない。AI が書いたことを相手に名乗るかは未決
- 決済は本人のカード。HelloPay の PCI DSS で番号を保管し、毎回本人が打つのは CVV と本人認証だけ（2026-11-20: CVC と本人認証のコードはアプリ内のフォームで受ける。「電話・ブラウザ」）。次は Cookie 引き継ぎで端末の Apple Pay、本命は Visa・Mastercard のエージェント用トークン（採らない案と要確認は decisions.md）
- 2026-09-25 追記: 決済の主方式は HelloPay for Agents（ライフカードを BIN スポンサーにした取引ごとの使い切りバーチャルカード）に変更。Live View は、for Agents が間に合わない場合の最初の決済方式、かつ動いた後の例外用（プリペイドを弾く店・決済以外の認証・発行側の障害時）。仕組み・損益・ロードマップは hello/hello-pay.md

## 画面（2026-09-26 決定）

タブは 6 つ。Hello / チャット / カレンダー / 電話 / メール / 自分（2026-09-27 にメールを追加。メールは初期リリースに含めないので、初期は 5 つ。2026-11-20 にカレンダーを追加。並び順は未決）。Muse（5 タブ: チャット・フィード・Ideas・Goals・ファイル）と同数だが、Muse に無い 3 つ（友人の部屋・電話・メール）を持つ。

電話とメールは記録の置き場。操作はできるが、通常は Hello タブで Hello から来たものに答えるだけで用事が終わり、開く必要がほぼない。

- Hello: 自分のアシスタントとの会話 1 本。サブチャットは作らない。上部に進行中の用事を 1 件 1 行で常に出す（「○○に電話中」「田中さんの Hello と調整中」）。3 件までは全部、4 件以上は本人の操作待ち（承認・引き取り・質問）を先頭にして残りを「ほか n 件」に畳む。タップで操作記録と一覧が開く。通話中もこの帯で見せ、画面全体は変えない。この会話はチャット一覧には出さない
- チャット: 友人との部屋の一覧。部屋は相手ごとで、人とそれぞれのアシスタントが同居する。部屋に出るのは人の発言と、誰の発言でもない事実の行（「金曜 19 時 ○○（4 名）に決定。予約は山田さん名義」）。アシスタントが部屋に何か出す時は必ず本人の承認を取る。Hello タブに文案が来て、本人が OK すると「山田さんの Hello」として部屋に出る。文案を出すのは用事を始めた人のアシスタント。部屋で @Hello と呼んだ時は呼んだこと自体が承認で、呼んだ人のアシスタントがその場で答える。自分のアシスタントから本人への文（「あなたの席は押さえました。会費 4,000 円」）と本人だけへの質問は Hello タブに部屋の名前つきで届く。メイン画面で使うカード（承認・進行中の用事など）は部屋でも同じものを使う。自分のアシスタントへの指示は、部屋の「Hello」ボタンからでも、メイン画面から「田中さんに○○して」と言う形でもよい（相手には見えない）。どちらで話してもメイン画面の会話に部屋の名前つきで残る
- 電話: 発信の履歴・着信の記録・自分の番号。通話は 1 本ずつ
- メール: Hello アドレスと接続した Gmail 等に届いた・送ったメールの履歴を全部残す。AI が先に読み、本人の判断が要るものは返信案つきで Hello タブに上げ、予約確認・注文・請求・配送は記録に落とす。検索は当面なし
- 自分: 記憶 / 委任ルール 3 つ / 承認の頻度 / 連携先 / 支払い / 番号と本人確認 / メールアドレス
- 承認はチャット内のカードで Muse と同じ 5 択（1 回だけ / この用事の間 / このサイトでは / 常に / 拒否）。「常に」と「このサイトでは」は委任ルールに書き込まれる
- 持たないもの: フィード・Ideas・Goals のタブ、サブチャット（Muse から借りない）

## 課金と原価（2026-09-27 決定）

プランは 3 つ。差は量だけ（Muse と同じ）。ここでは儲けない。稼ぐのは toB 側（予約サイト・店・決済）。

| | 無料 | 1,980 円 / 月 | 9,800 円 / 月 |
|---|---|---|---|
| 電話 | 月 40 分 | 月 120 分 | 月 240 分 |
| トークン | 月 1,000 万 | 月 5,000 万 | 月 2.5 億 |

- 電話は無料でも使えるが、番号発行のために本人確認が要る。無料の電話は番号発行日から 3 ヶ月の試用で、以後は有料にしないと番号を解放する。期限が来たら「有料にするか、番号を手放すか」を選ばせる。自動課金はしない
- 有料化の引き金は 2 つ。3 ヶ月の期限と、無料のトークン上限。有料 2 つの上限は平均的な使い方では届かない量で、乱用の歯止めとしてだけ効く
- 課金はアプリ内と Web（HelloPay）の両方で、比率は半々と置く。iOS の手数料は、アプリ内 21〜26% / アプリ内リンク経由の Web 購入 15% / リンクを経ない Web 購入 0%。番号と通話分は「アプリ外で消費されるサービス」に近いが、トークンと混ぜたプランで IAP 免除を主張すると審査で落ちる可能性が高い
- Muse は週 1 億 / 5 億 / 30 億トークン（無料 / 20 ドル / 100 ドル）。数え方が違うので数字を並べて比べない

原価の前提（数字は 2026-09-27 時点。推測は明記）

## カレンダー（2026-11-20 決定。正本は GitHub hello-ai/hello #3184）

部屋で作った予定も、外のカレンダーの予定も、1 つの表で見る。Hello が取りに行くのは、Hello を正本にした予定と、全部を 1 つの表で見る体験。

- 入口はタブ。表示は日・週・月・一覧。追加・編集・削除・出欠は画面からも Hello との会話からもできる。デザインは Notion Calendar をベースにする
- 1:1 の部屋で作った予定は相手の人を招待する。複数人の部屋はグループとして扱い、予定はその部屋（部屋の ID）を招待する。名前のある部屋は人が増減しても部屋の ID が変わらない
- 複数人の部屋の予定は Google グループと同じ動き。日時が先の予定の参加者は部屋の今のメンバーで、入れば加わり抜ければ外れる。過ぎた予定はその時点の参加者で固定する
- 出欠は人ごと。自分の表に出るのは「行く」と「未回答」だけ。1:1 の部屋には 2 人とも参加者の予定（外のカレンダーから同期した物も含む）、複数人の部屋にはその部屋が招待先の予定だけを出す
- 他人の予定を見せる範囲は relation.md で決める
- 外のカレンダー（Google・Outlook・iPhone）は区別せずに同期し、Hello に写しを持つ（表示・空き時間の判定・日程調整を速くし、外の変更に気づくため）。仕事かプライベートかでは分けない
- 予定ごとに正本のカレンダーを 1 つ持つ。どこに作るかは相手と過去の予定から Hello が選び、既定は Hello。外が正本の予定は変更と出欠を外に書き戻す。Hello が正本の予定は外に書き戻さない（「予定あり」の書き戻しは、日程調整を Hello でやるようになれば不要になるので作らない）
- 予定は自前の DB に持ち、iCalendar（RFC 5545）は外とのやり取りにだけ使う。繰り返しは RRULE・EXDATE・RECURRENCE-ID と同じ考え方で持つ。タイムゾーンは開始と終了で別に持つ。外の予定の ID（iCalUID など）で二重表示を防ぐ
- Hello が無い相手はメアドで招待できる。Hello のメアドから「播口 via Hello」で iCalendar の招待メールを送り、相手は自分のカレンダーで出欠を返せる（登録なしで答えられる経路。「連絡先とチャット」の「登録なしで答える経路は最初は出さない」の例外）。メールの下半分に「播口さんと Hello でつながりませんか？」と招待 URL を置く
- 招待メールのボタンから登録したら、招待した人と自動でつながる。カレンダーをつないで招待の予定が見つかった場合は、お互いに「つながりますか」と候補を出す。カレンダーをつながない人の分は結びつけない（漏れても実害が小さく、作りが単純になる）
- 同じ人がつながりに 2 件ある時は、Hello が「この人と同じですか」と聞いてまとめる

## 招待 URL（2026-11-20 決定。#2491）

- 招待 URL は 1 人に 1 つ。つながりを追加する画面の「リンクを送る」・QR コードと同じ物。期限なし、何回でも使える。「QR コードを更新」で作り直す。不要な相手はブロックで外す（ID が分かれば追加できるのと同じ扱い）
- アカウントのないつながりの［招待］は、この URL を共有シートで開き、本人が LINE などで送る。Hello からは送らない
- 開いた画面は「播口さんと Hello でつながりませんか？」と 1 ボタン。登録すると招待した人と自動でつながる
- 上の「バイラルの入口は共有 URL」（文脈つき・期限つき）は用事の招待。文脈の無いつながりの招待はこの固定の URL

## つながりかも（2026-11-20 決定。#3226）

- つながりに載せるのは、Hello の中で何かしら一緒に動いた人だけ
- カレンダーをつなぐと、一緒に予定に入っていた人を「つながりかも」に出す。つながりの一覧で「アカウントのないつながり」の下に 1 行置き、中身は一緒の予定の件数順。名前が取れなければメアドで出す
- 利用者には［追加］、未登録の人には［招待］。招待するとアカウントのないつながりに入る
- 招待は Hello のメアドから「播口 via Hello」で送る。宛先と文面を本人が確認し、1 人に 1 回だけ、催促なし、配信停止のリンク付き
- Hello が追加や招待を促すのは、直近の予定に入っている時・会話に名前が出た時・一緒の予定がまた増えた時だけ。定期的には促さない

## 予定を追加した時の招待（2026-11-20 決定。#3253）

- Hello が予定をカレンダーに追加したら、「○○さんも招待しますか」と聞く。候補はつながりの中から、予定が出てきた文脈で推測する（チャットで決まった予定なら、そのチャットや部屋にいる人）。候補がいなければ聞かない
- 利用者には予定が直接届く。未登録でメアドが分かれば招待メール（#3184。仕事で使う相手もいるので、登録なしで出欠を返せる）。メアドが分からなければ予定の共有 URL を作り、本人が LINE などで送る
- 共有 URL は登録なしで予定を見られるが、出欠は置かない。URL から登録すると、送った人と自動でつながり、予定が自分のカレンダーに入る。登録すると予定の管理が楽になることと、ほかの Hello の良さを見せて登録を促す

## 住所を知らずに送る（2026-11-20 整理。#2483）

- 相手の住所を知らなくても物を送れる。相手の AI アシスタントが相手の住所で普通の EC に注文し、送る側は自分のカードで払う。ギフトに限らず、はがき・内祝い・花・フードデリバリーなど Web で頼めるものは全部この仕組みで送る（「ギフト」の名前にしない）
- 物の決め方は 3 つ: 受け手の欲しい物から選ぶ / 予算を言って受け手の AI アシスタントが返した候補から選ぶ / 自分で選んだ物を伝える。受け手の AI アシスタントが住所を入れて支払いの直前まで進め、送る側がフォームで CVC と本人認証のコードを打って確定する
- つながりの人には何でも送れる。受け手の AI アシスタントが「○○さんがこれを送りたいと言っています。受け取りますか？」と物を見せて聞く（サプライズより、受け手が断れることを優先）。欲しい物から選んだ物は聞かない。つながりにいない人は公開 URL から、欲しい物にある物だけ
- 送る側は登録してから払う。お金は店に直接払われ Hello を通らない。残高は持たない
- 送る側には Live View を出さない。送る側の操作は Hello の中のフォームで終え、届くのは「注文しました」「届きました」だけ
- セキュリティで必ず守ること（#2483「セキュリティ」）: 受け手の住所を送る側と AI 同士のやり取りに出さない / カード情報は PCI DSS の範囲だけを通し、受け手の EC に残ったカードは消して確かめる / 承認した商品と金額でしか払わない / 公開 URL の相手には送り物以外を答えない / ページや文に書かれた指示で配送先や支払いを変えない

## 欲しい物（2026-11-20 整理。#3274）

- 欲しい物は 1 人 1 つの wants.md に持つ（relation.md と同じ形）。本人が Hello に「欲しい」と言った物が、1 行 1 つで自由文と商品の URL で溜まる。全文が部屋の人に見える前提で書き、見せたくない物は入れない。履歴は持たず、送られた物・買った物は行ごと消す
- 自分タブに「欲しい物」の行を置き、部屋にカードを送るとその部屋の人に見える。カードは送った時の一覧のまま。送ろうとした物がもう wants.md に無ければ、本人に新しいカードを送ってもらう。「欲しい物を○○さんに見せますか」の答えはその人の relation.md に書き、次からは聞かない
- 公開 URL（クリエイター向け）はランダムな文字列の URL で再発行できる（ユーザー名は入れない）。既定は非公開。wants.md の全部を開くたびに読んで出し、画像は商品ページの OGP の画像 URL をそのまま表示する（保存しない）。ページは Web だけで、アプリに相手の欲しい物の画面は作らない（ユニバーサルリンクは「送る」のリンクだけ）
- 公開 URL からはつながりにいない人も送れる。アプリが入っている人は「送る」でアプリが開き、Hello タブの入力欄に「○○さんに○○を送りたい」が入る（送信は本人）。未登録の人は「送る」を押した時に Web で登録し、支払いまで Web で終える（アプリは送った後に勧める）。公開 URL から送っても受け手と自動ではつながらない（ファンが大勢つながりに入るのを防ぐ）

## 部屋のアルバム（2026-11-21 整理。GitHub hello-ai/hello #3307）

- 純正で作る。アルバムのデータ（タイトル・表紙・写真の ID の並び）は参加者・チャット・カレンダーと同じ部屋の共有データとして持ち、あとでスペース（部屋のデータをどう加工して見せるかを決める物）からも使えるようにする
- 写真は部屋に 1 枚、アルバムは入れた印だけ。消せるのは自分が足した写真だけ。有料プランは元の画質、無料は長辺 2,048px 程度。動画は無料でも保存できる
- 写真を外す時は「アルバムから外す」か「写真を消す」（足した本人だけ。全アルバムとトークから消える）を選ぶ。アルバムは部屋のメンバー全員が見られる
- コメントとリアクションはトークと同じデータ。コメントはトークに写真への返信として出て、リアクションはトークの写真のメッセージにも付く（2026-11-21）
- カレンダーの予定が終わった翌日に、参加者それぞれの Hello が「アルバムを作って、この写真を載せますか？」と 1 回で聞く。載せない写真は外せる。最初に載せた人の写真でアルバムができ、後の人は足す。誰も載せなければ作らない（2026-11-21）
- 顔で自動分類する。分けるのは本人が ON にした人と、親が登録した子どもだけ
- 部屋を抜けた時の写真の持ち出しは作らない

## 位置情報の共有（2026-11-18 決定。#3006）

- 相手ごとの状態は「毎回聞く」（既定）と「見せる」の 2 つ。「答えない」は作らない。「見せる」には期限（1 時間・着くまで・日時）か無期限が付き、切れたら「毎回聞く」に戻る。無期限は本人が自分から始めた時だけ。継続の定期確認はしない
- 聞かれたら、会話の中に自分だけに見えるカードを出す。選択肢は「今の場所だけ教える / しばらく見せる / 教えない」。「しばらく見せる」は Hello が期限を聞く
- 見せている間は、会話のライブの地図カードの中に相手・期限・［止める］を出す。教えなかったこと・止めたことは相手に伝えない
- 状態と期限は relation.md に値で持つ。全員に効く制限は位置情報の connect.md、相手ごとの条件は relation.md に書き、厳しい方を採る
- グループ: 共有は相手ごとのまま。部屋の地図には、自分に見せてくれているメンバーだけ載る。「みんなに場所を見せる」はメンバー全員への一括。止めるのも一括で、前から個別に見せている相手は対象外

## 連携アプリ（2026-11-18 決定。#3074 詳細、#2482 一覧）

- 「コネクター」と呼ばず「アプリ」で統一する（画面名は「連携アプリ」）。ファイル名の connect.md はそのまま
- 詳細画面はどのアプリも同じ 3 部品: アカウント / 確認（毎回確認・Hello が判断・任せる。既定は Hello が判断）/ 扱い方（connect.md をそのまま整形して出す。直すのは Hello に言う）。操作ごとの許可の行は廃止
- 支払いと予約の確定は、確認の選択に関係なく毎回確認する
- MCP・CLI・ブラウザ操作のどれでつないでも同じアプリとして扱い、つなぎ方は利用者に見せない。ブラウザ操作で始め、提供元が接続口を出したら裏側だけ替える（本人には切り替えを 1 回提案する）
- チェックマーク（✓）: 提供元の会社自身が公開している接続口（API・MCP・CLI）でつなぎ、Hello が確認した物にだけ付ける。確認済みの接続先の一覧は Hello が運用する。第三者の MCP・CLI、ブラウザ操作、利用者が足した物には付けない。「公式」などの言葉は付けない（Google APIs 利用規約 6 条(c) が、承認なしに提携・公認を示唆する表現を禁じているため。法務の確認は未了）
- 一覧は、みんながログイン・MCP・CLI でつないだ物を網羅して、国ごとに、つないでいる人数の順で並べる。同じサービスは 1 行にまとめる。人数も出す（出し方は未決）
- 他社（2026-11-18 確認）: Muse は操作ごとに「許可する / リクエストする」を選ぶ。Grok は書き込みをまとめて 1 行（自動レビュー）で決める。公式側の作りは、Muse が API か MCP、Grok の標準は自社で組み込んだ OAuth の連携。利用者が自分で足す分は、どちらも MCP。OpenTable は Muse のローンチパートナー（OpenTable 自身の発表）
