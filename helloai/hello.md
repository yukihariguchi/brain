# Hello（パーソナルアシスタント）

汎用パーソナルアシスタント。プロダクトは Hello、会社は HelloAI（新設する株式会社HelloAI）と呼ぶ（2026-11-18。10-16 の社内呼称 Hello Assistant / HA は廃止。サービス名 Hello は 2026-09-24 決定）。
HelloAI の立て付けは reorg.md「全体像」、移す前の体制は hello/base.md。課金と原価は helloai/pricing.md。
機能ごとの仕様の正本は GitHub hello-ai/hello のイシュー。ここには骨格と番号だけ置く（2026-11-22 に整理）。

## 作り方の方針（2026-11-18 整理）

出所は Slack #ha-general / #ha-dogfooding の播口の発言。かっこ内は発言日（2026 年）。

- 固定の設定 UI を増やさない。設定は AI との会話でやり、中身は md に自然言語で持つ（11-01、11-06）
- 自前で作るのは電話・チャット・決済だけ。ほかは Muse・Grok と同じ実装にする（10-15）
- AI は 1 つ、会話は 1 本。サブチャット・複数アシスタント・グループの統括 AI は作らない（10-01、10-19、10-23）
- 外部連携は自前で実装しない。MCP があれば MCP、無ければ Skills + CLI。認証は sandbox の外に置く（10-15）
- 日本・韓国・台湾ほかアジアを Muse より先に取る。最初から全世界対応で出す（09-27、11-01）
- 本人が言わなくても覚え、提案する。目標は「提案に OK を押すだけで回る」（11-14、11-16）
- イシューにはやりたいことだけ書き、細かい仕様はエンジニアに任せる（11-21）

## 何をするサービスか（2026-09-24）

Muse・ChatGPT・Gemini と同じ種類の汎用パーソナルアシスタント。頼まれた用事を本人の代わりに終わらせる。

- 当たり前にできること（他社と同水準。差にはならないが無いと選ばれない）: 予約サイトを横断して比べて予約する / EC で探して買う / フォームの入力・会員登録・問い合わせ / 旅程や日程の調整 / 記憶を使って次の依頼を短くする
- 他社より優れているところ: 電話と決済。相手が API も Web も持たない現実世界（店・病院・業者・役所）に電話で届き、決済まで本人のカードで完結させる
- チャットとつながりを Hello の中に持ち、LINE を disrupt する。友人と普通に会話でき、同じ部屋にパーソナルアシスタントが居て用事を引き受ける

## 守りはつながりの数（2026-11-22）

Hello の守り（moat）は、つながりをどれだけ増やせるか。友人も含めて Hello に入るほど、やりとりと記憶が溜まり、Hello がその人を理解していく。

- 普通の AI アシスタントは、本人の友人とやりとりできない
- Gmail などを連携しても、届くのはメールする相手だけ。友人との日常のやりとりは LINE の中にあり、AI からは見えない
- Hello はチャットと部屋を持つので、友人とのやりとり・予定・写真・相手ごとの relation.md が Hello の中に溜まる
- つながりが増えるほど、Hello の理解が深まり、他の AI に移りにくくなる
- 招待 URL・つながりかも・予定を追加した時の招待は、この守りを積むための入口
- 根本は、いろんな場所に Hello を登場させ、md が勝手に更新されていくこと。友達との会話は GPT も Claude も持たないので、かゆいところに手が届かない（Slack #pa-general 11-22）
- Slack などの会話もどんどん取り込む。外部サービスでも人を対応づけて、サービスごとのソーシャルグラフを作り、md にまとめる（同上。イシュー化は播口）

狙う仕事（Slack #pa-general 11-22、田中との会話）

- 人にコンテキストを伝えるだけの仕事をなくす。資料作り・Slack のやりとりの多くはこれ
- フォルダ分けも考えさせない。整理は全部 Hello が自動でやる
- 会議の文字起こし（Notta など）を全部取り込み、Hello が会議に出た関係者にメンションする。いずれは Hello が会議に参加して自分でやる（河野に依頼）
- 営業のネクストアクションも Hello に任せる。HelloCloud の業務で使い、足りない機能は田中が PR を出すこともある

## 早い者勝ちが成立する条件

パーソナルアシスタントは一度選ぶと変えにくい。だから日本では一番最初に出す。「最初」は「AI が電話をかける」ことでなく、実況・途中の指示・本人の引き取り・本人名義の番号・決済まで揃えた形で最初、という意味（AI が電話をかけるだけなら Genspark が先にあり、使われていない）。Muse・Agent i・Google が日本で使える形になる前に、Hello を選んだ人を作る。

残るのは切替費用が積まれた分だけ。取った数より、1 人あたりに積まれた量が守りの厚さ。

- 積まれるもの: つながりと、つながりとのやりとり（2026-11-22）/ 本人が外に出した Hello の番号とメールアドレス（店・病院・宅配の連絡先に入る）/ 記録（どこに何を頼み、何と言われたか）/ 保存済みのログインセッションとカード / 委任の設定
- 積まれないもの: チャット画面、モデルの賢さ、実況の UI。相手が同じ物を出せば差が消える
- テスター版から「番号を外に出す」「記録を残す」は落とさない

## 電話（2026-09-25 更新）

Hello ができること

- Hello がユーザー 1 人 1 人に付与した番号から AI が電話をかける。予約だけでなく、行列や空席や在庫を聞く、見積もりを取る、変更やキャンセルや再配達の手続き、保留や自動音声の待ち
- 本人は文字起こしを実況で見て、途中で自由文で指示できる。いつでも自分が出られ、終わったら AI に戻せる。AI が続けられない場面は本人を呼び、出られなければ「折り返します」と言って切る
- 3 軒に聞くなら順にかけて、答えを表で返す。通話は 1 本ずつで、メイン画面がそのまま通話画面になる
- 着信も AI が受ける。店の折り返しは用件を解決し、宅配や業者は用件を文字で渡し、営業電話は切り、大事な電話だけ本人に繋ぐ
- 日英仏伊西独。本人が引き継いだ後も同時通訳が入る
- 通話の内容は全部本人の記録に残る
- 発信でも着信でも、相手がどこかを番号から AI が調べて表示する（11-17。実装予定）

決定

- 代理電話の引き継ぎは本人がやる。運用部隊は使わない（09-24）
- 1 人 1 番号。番号が無いと折り返しを受けられない。配れない国は発信だけで出す（11-17）
- 日本は 050 を本人確認つきで発行する。050 は SMS 非対応なので電話から。本人確認は電話機能を使う時に求め、チャットや招待は本人確認なしで使える（09-24）。韓国は通信事業者の登録が要り未決。台湾は調査中（11-17 時点）

他社との差

- Google: 2026-09-24 に「Call for Me」を米国の Pixel 11・有料 Gemini 向けに開始。本人が実況を見て引き取れる発信はもう独自ではない。日本語・Pixel 以外・日本での提供は無い。日本語版が出た時点で残る差は Hello 名義の番号への着信・決済・チャット。優位の寿命は 12〜24 か月と置く（推測。毎月の競合比較で見直す）
- Genspark: 2025 年から日本語の代理電話を提供。本人が引き取れず、日本語の音声の精度が低いため、ほぼ使われていないと見る（播口の見立て。利用実態は要確認）
- Apple: iOS 26 で着信スクリーニングと保留待ちが日本語対応。発信の代行は無い
- Meta Muse: 電話を人のコールセンターに隠れてやらせて叩かれた（2026-09）。米国限定・英語のみ
- LINE ヤフー Agent i: トークルームの中で予約・購入。電話は無い

Hello に残る差は 4 つ。日本語で今出せること / 本人名義の番号で発信し着信も受けること / どの端末でも使えること / 電話の先で決済まで完結すること

## 決済

- 主方式は HelloPay for Agents（ライフカードを BIN スポンサーにした取引ごとの使い切りバーチャルカード。hello/hello-pay.md）。本人は最初に 1 度カードを登録し、以後はチャットで OK を押すだけ。電話の先の相手にも、その場で決済まで届く（09-25）
- for Agents が公開に間に合わない場合の最初の方式は、本人のカードを HelloPay の PCI DSS で保管し、コードが埋める。CVC・3D セキュアのワンタイムコード・パスワードはアプリ内のフォームで受け、保存しない（11-20。Grok・Muse もフォームで受けている）
- Live View（エージェントのブラウザを本人の端末に映し、本人が打つ）は例外用。プリペイドを弾く店（ホテルの与信枠・レンタカー・一部のサブスク）、決済以外の認証（ログインの 2 段階認証）、発行側の障害時。打鍵は映像と同じ経路で遠隔ブラウザに届き、Hello のサーバーと LLM は値を持たない
- 次は Cookie 引き継ぎで端末の Apple Pay、本命は Visa・Mastercard のエージェント用トークン（採らない案と要確認は decisions.md）

電話 × 決済で Hello にしかできない 3 つ

1. カード保証つきの予約電話: 無断キャンセル時にデポジットが取れる予約として店に伝えられる。店が AI の電話を受ける理由になる
2. 電話で交渉して、その場で払う: 見積もり → 交渉 → 支払いまで 1 本の電話で終わる
3. 相手も HelloX なら音声でなくデータで済む: 導入先が増えるほど完了率が上がり、日本語の音声 AI の精度問題を飛ばせる

## チャットと部屋（2026-09-24 決定）

チャットを持っている側は、用事の入口と人の関係を握る。LINE がこれを持っている限り、Hello の予約や電話は LINE の会話の下請けになる。だからチャットは後回しにせず、早めに引き剥がしに行く。

LINE は人が先に友だちになって部屋ができる。Hello は用事が先にあり、答えた瞬間に部屋ができる。部屋にはアシスタントが居るので、人が黙っても部屋は死なない。

- 部屋は相手ごと。参加者は人と、それぞれのアシスタント
- アシスタントが部屋に何か出す時は必ず本人の承認を取る。Hello タブに文案が来て、本人が OK すると「山田さんの Hello」として出る。@Hello と呼んだ時は呼んだこと自体が承認
- アシスタント同士が日程・条件・支払いを詰める。部屋には確定した事実だけが 1 行で残り、過程は見せない。自動で決める範囲は本人の委任ルール 3 つ（曜日と時間帯・予算・食の制約）（09-27）
- 連絡先は取り込まない。用事を一緒にした人が積まれてつながりになる。Hello 同士はユーザー名で追加できる
- 「友達に送って」は Hello 同士なら直接届く。LINE・Instagram の API の制約を、相手を Hello に連れてくることで越える
- チャットの UI は LINE に揃える（入力欄・スタンプ・リアクション・ピン留め）。消えるメッセージは Telegram と同じ仕様（11-18）
- 返信案は出さない。オン・オフの設定も作らない（11-18）
- メッセージはサーバー側の鍵で暗号化し、社内でも SQL で読めないようにする。端末間の暗号化（E2EE）は AI が読めなくなるので採らない（11-17）

バイラルの入口は共有 URL（09-24）

- 質問でなく招待として見せる。「○○さんがあなたと金曜か土曜に恵比寿で食事をしようとしています」を相手のアシスタントが語り、「Hello に入って続ける」の 1 ボタン。登録すると予定と自分のアシスタントが待っている
- URL の裏は「誰から・文脈・目的・範囲」の 4 つだけで、集まり・予約の共有・日程調整・電話で聞いた結果・割り勘まで同じ形で通す。期限は文脈で自動
- リンクの検知はアカウントで行い、端末の推定（deferred deep link）に頼らない
- 入らない人は幹事のアシスタントが代弁する。登録なしで答える経路は最初は出さない（例外はカレンダーの招待メール）

検討中（11-18 夕方時点。明示の決定は無い）

- Hello の提案は、会話の間に「あなただけに表示」の発言として挟む。消す条件（30 通か 3 日）は未回答
- Hello が予約を確定まで進めるか。今は確定ボタンの手前で止まる

## 画面

タブは 6 つ。Hello / チャット / カレンダー / 電話 / メール / 自分（09-26 決定。09-27 にメール、11-20 にカレンダーを追加。メールは初期リリースに含めない。並び順は未決）。

- Hello: 自分のアシスタントとの会話 1 本。上部に進行中の用事を 1 件 1 行で出す。3 件までは全部、4 件以上は本人の操作待ちを先頭にして残りを畳む。チャット一覧には出さない
- チャット: 友人との部屋の一覧
- 電話・メール: 記録の置き場。通常は Hello タブで答えるだけで用事が終わり、開く必要がほぼない
- 自分: 自分のこと → ファイル → つながり → 連携サービス → 欲しい物、の順に並べ、その下に設定（11-22）
- 承認はカードで Muse と同じ 5 択（1 回だけ / この用事の間 / このサイトでは / 常に / 拒否）。「常に」と「このサイトでは」は委任ルールに書き込まれる
- 持たないもの: フィード・Ideas・Goals のタブ、サブチャット

## 記憶: md に持つ（2026-11-18 整理）

Hello が覚えることは md に自然言語で持つ。Hello が会話から書き、本人は直接書かない。直したい時は Hello に言う。本人に見せる時は記号を見せず、整った見た目で出す。

- relation.md: つながりごとの文書。関係・その人の情報・その人に見せてよい範囲。実装は contact_notes テーブル。system context には index だけ入れ、中身は必要な時に読む。アカウントの無い人も同じ仕組み。本人はその人の画面の「○○のこと」で見られる（11-17）。友達を追加したら Hello が関係を聞き、最初の relation.md を作る（11-18 実装済み）
- connect.md: 連携サービスごとの文書。使い方と制限（例: このカレンダーは自分の予定として扱わない / 削除は必ず確認する）。変更はカードで本人の許可を取る。許可が要るかの判定はメインと別のモデル（11-06）
- wants.md: 本人の欲しい物（#3274）
- 自分のこと: 上の 3 つ以外のテーマ（仕事・家族・旅行など）の文書も Hello が作る。「この話は○○さんに話していい」と言えばその人の relation.md に残り、相手の Hello に聞かれたら許した範囲で答える。文書そのものは見せない（#3320。11-22）
- 公開範囲は 2 か所に書く。サービス側は connect.md、相手側は relation.md。両方ある時は厳しい方を採る（11-18）

## 機能（正本は GitHub hello-ai/hello）

つながり・招待

- つながり（#3018）: 一覧はアカウントのある相手の名前順。アカウントのない相手は 1 階層下。Hello の中で一緒に動いた人だけ載せる
- 招待 URL（#2491）: 1 人に 1 つ、期限なし。登録すると招待した人と自動でつながる。文脈つきの共有 URL とは別物
- つながりかも（#3226）: カレンダーで一緒の予定に入っていた人を候補に出す。招待は 1 人に 1 回だけ、催促なし
- 予定を追加した時の招待（#3253）: 予定を入れたら「○○さんも招待しますか」と聞く
- 名前の表示（#3029）: 相手ごとに本名かニックネームかを選ぶ。見る側の上書きは無し
- 位置情報の共有（#3006）: 相手ごとに「毎回聞く」（既定）と「見せる」（期限つき）の 2 つ。状態は relation.md に持つ

カレンダー・部屋

- カレンダー（#3184）: 部屋の予定も外のカレンダーも 1 つの表。予定ごとに正本を 1 つ持ち、既定は Hello。Hello が無い相手には「播口 via Hello」で招待メールを送り、登録なしで出欠を返せる
- 部屋の写真（#3307）: 純正。部屋の写真の一覧 1 つで、アルバムは作らない。撮り終わったら Hello が「部屋に上げますか？」と聞き、本人は答えるだけ
- アプリ / Hello Apps（#3311）: つながりを使える App Store。利用者は会話で、開発者は Claude Code や Codex で AI に作らせる。Hello との連携が売り
- DayLog（#3310）: setlog のような友だち同士の Vlog。Hello Apps で作る最初のアプリ

送る・買う

- 住所を知らずに送る（#2483）: 相手の AI アシスタントが相手の住所で EC に注文し、送る側は自分のカードで払う。受け手の住所は送る側に出さない
- 欲しい物（#3274）: wants.md に溜め、部屋にカードで見せる。公開 URL はクリエイター向け

連携・記憶

- 連携サービス（#3074 詳細、#2482 一覧）: 詳細画面はアカウント / 確認 / 扱い方の 3 部品。支払いと予約の確定は毎回確認。つなぎ方（MCP・CLI・ブラウザ操作）は利用者に見せない。✓ は提供元自身の接続口で、Hello が確認した物だけ
- 公式パートナーの申請（#3078）: 提供元が接続口を申請し、審査を通ると ✓ が付く。最初の 1 社は AutoReserve の想定
- ファイル（#3319）: Google Drive のような置き場。文書は Hello が会話から作る。個人にもグループにも共有でき、権限は閲覧 / 編集 / 編集と招待。リンクでの公開はしない
- 自分のこと（#3320）: 上の「記憶」
- 取り込み（#3322）: 他の AI の記憶・会話の書き出し・フォルダを取り込み、自分のこととファイルに振り分ける。オンボーディングにも入れる
- 本人の ChatGPT の契約で動かす（#3321）: Sign in with ChatGPT で、DeepSeek の代わりに本人の ChatGPT の枠を上限まで使う。使い切ったら Hello のプランの範囲で DeepSeek に戻る。Claude は契約の流用を規約で禁じているので対象外
